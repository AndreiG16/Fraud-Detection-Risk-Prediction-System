01 The Problem

You have 284,807 credit card transactions and need to flag the 492 that are fraudulent — without being told which features mean what, because Visa anonymised them into PCA components V1–V28 for privacy.

The challenge isn't the algorithm. It's the imbalance. Fraud makes up 0.17% of all transactions. A model that labels everything as "legitimate" scores 99.83% accuracy. That model is completely useless — it misses every single fraud case. Almost every decision in this project is a direct response to that one fact.

The core tension: Banks care far more about catching fraud (recall) than about false alarms (precision). Missing a real fraud case can cost thousands; flagging a legitimate transaction annoys the customer. Your models have to balance this — and the metric you pick determines what "balance" means.

02 EDA Findings

🔢

No missing values

All 31 columns across 284,807 rows are fully populated. No imputation strategy needed — simplifies the pipeline significantly.

⚠️

1,081 duplicate rows — but not blindly dropped

Before removing duplicates, we checked the class split: 1,062 were legitimate, 19 were fraud. Fraud cases were already rare (492 total), so losing 19 more (~3.9%) was worth noting explicitly. We dropped them anyway — they're almost certainly data-collection artifacts — but the check itself is worth mentioning in interviews.

📊

Amount is heavily right-skewed

Mean transaction is $88, median is $22, max is $25,691. The distribution has a very long tail. For scale-sensitive models (Logistic Regression, distance-based), this needs fixing. We applied log1p(Amount) to compress the tail and make the feature more Gaussian-like.

🕐

Time re-engineered as hour-of-day

The raw Time column is seconds since the first transaction — a monotonically increasing counter with no predictive meaning on its own. We converted it to hour_of_day = (Time / 3600) % 24 to capture the natural daily cycle of legitimate vs. fraudulent activity patterns.

Why stratified?

A random split of 283,726 rows with only 473 fraud cases could put all the fraud in the training set by bad luck. Stratified split guarantees the fraud rate is preserved in both halves: the training set gets 378 fraud cases, the test set gets 95.

Data leakage trap: If you scale first (on the whole dataset) and then split, your scaler has "seen" the test set's distribution when computing the mean and standard deviation. The test set is no longer truly unseen. Same problem with SMOTE — if you oversample before splitting, synthetic fraud examples generated from test-set fraud transactions leak into the training data. Always split first.

04 Scaling

We applied StandardScaler — zero mean, unit variance — to all features. The scaler is fit only on the training set, then used to transform both train and test.

V1–V28 are already PCA-transformed and reasonably well-scaled, but log_amount and hour_of_day are on completely different scales. Without scaling, a Logistic Regression model would weigh a unit change in V1 the same as a unit change in Amount, which can be hundreds of dollars. Tree models (Random Forest, XGBoost) are scale-invariant, so scaling doesn't change their performance — but it doesn't hurt either, and it keeps the pipeline consistent.

05 Handling Imbalance — SMOTE

SMOTE (Synthetic Minority Over-sampling Technique) generates synthetic fraud examples by interpolating between real ones in feature space. Instead of just duplicating existing fraud cases, it creates new ones that lie along the line segments connecting nearby fraud transactions.

Why SMOTE on train only? SMOTE artificially inflates the minority class. If you applied it before splitting, synthetic fraud transactions would end up in the test set — and you'd be evaluating your model on made-up data, not real fraud. The test set must reflect the real world: 0.17% fraud.

Why not just use class_weight="balanced"?

Class weights are simpler — they tell the model to penalise fraud misses more heavily during training. We actually use both: SMOTE for the data itself, and XGBoost's scale_pos_weight as an additional signal. For Logistic Regression and Random Forest, class weighting alone can work well. SMOTE gives the model more real-looking fraud examples to learn from, which helps tree models find better decision boundaries.

06 Model Choices

📏

Logistic Regression — the baseline

Every serious ML project starts with a linear baseline. If a more complex model can't beat logistic regression, either the features aren't powerful enough or the complex model is misconfigured. LR also gives you probability outputs and is highly interpretable — you can read the coefficients directly.

🌲

Random Forest — ensemble of decisions

Builds 200 decision trees on random subsets of data and features, then averages their predictions. More robust than a single tree, handles non-linear relationships, and is naturally resistant to overfitting. Also scale-invariant — no need to worry about the scaling step affecting it.

⚡

XGBoost — sequential boosting

Rather than building trees in parallel like RF, XGBoost builds them sequentially — each new tree focuses on correcting the errors of all previous ones. It's typically stronger at finding subtle patterns in structured/tabular data. We set scale_pos_weight to the legit/fraud ratio as an additional imbalance correction.

💡

LightGBM — leaf-wise boosting

Similar philosophy to XGBoost but grows trees leaf-wise (deepening the most impactful leaf) rather than level-wise. Usually faster and sometimes more accurate. Good sanity check against XGBoost — if they agree, you can be confident in the result.

07 Why PR-AUC, not Accuracy?

With 0.17% fraud, accuracy is meaningless. A model predicting "legitimate" every single time scores 99.83% accuracy while catching zero fraud cases. We need metrics that tell us what's actually happening with the minority class.

Precision-Recall AUC (PR-AUC)

Precision = of everything flagged as fraud, how many were actually fraud? Recall = of all actual fraud cases, how many did we catch? The PR curve shows the tradeoff between these two as you move the classification threshold. PR-AUC (also called Average Precision) summarises the whole curve in one number — it is the primary metric for this project, because it focuses entirely on the minority class.

Why not ROC-AUC alone?

ROC-AUC looks at true positive rate vs. false positive rate. With so many legitimate transactions, even a weak model has a low false positive rate — making ROC-AUC look artificially high (all four models score 0.97+) even when performance on fraud cases is poor. PR-AUC is the harder, more honest metric for imbalanced data.

F1 Score

The harmonic mean of precision and recall at the default 0.5 threshold. Useful, but threshold-dependent. PR-AUC gives the full picture across all thresholds.

Winner: XGBoost with PR-AUC 0.8123 — the best at balancing precision and recall across all thresholds. It catches 82% of fraud cases (recall) while flagging a legitimate transaction roughly 41% of the time it raises an alarm (precision 0.59). In a real bank this threshold would be tuned — a fraud team can review more false positives if it means catching more real fraud.

Logistic Regression anomaly — why such low F1?

LR scores F1 of 0.098 despite recall of 0.87. It catches most fraud but floods the alerts with false positives (precision 0.05 — only 1 in 20 flagged transactions is actually fraud). That's what happens when a linear model meets highly non-linear fraud patterns after SMOTE has made the training set 50/50: it lowers the decision boundary so aggressively that it flags almost anything. The PR-AUC of 0.68 still reflects reasonable performance when you move the threshold — but at the default 0.5 cutoff it's impractical.

09 SHAP Explainability

SHAP (SHapley Additive exPlanations) tells you why the model made a specific prediction — not just what it predicted. It assigns each feature a score (SHAP value) that represents how much that feature pushed the probability toward fraud or toward legitimate, for that specific transaction.

TreeExplainer

For tree-based models like XGBoost, SHAP uses TreeExplainer — an exact algorithm that's far faster than brute-force Shapley computation. For a single transaction, it walks every tree and tracks how each split changed the prediction, then attributes the change to the features involved.

Reading the summary plot

Each row is a feature. Each dot is one transaction. Position left/right shows whether the SHAP value pushed toward legitimate (left) or fraud (right). Color shows the actual feature value — red = high, blue = low. A feature like V14 where low values are red and push right tells you: transactions with unusually low V14 are much more likely to be flagged as fraud.

Reading the waterfall plot

This shows a single transaction's explanation. Start at the baseline (the model's average prediction across all transactions). Each bar adds or subtracts from that baseline. Red bars push the prediction toward fraud; blue bars push it toward legitimate. The final prediction is the sum of all those pushes. This is what makes the Streamlit demo useful — every transaction gets a personalised explanation.

Interview line: "I used SHAP because accuracy metrics alone don't tell you whether the model is learning the right things. A model that scores well but relies on noise or spurious correlations will fail in production. SHAP lets me verify that the model is flagging fraud for interpretable, defensible reasons."

10 Interview Q&A

Q: Why did you use SMOTE instead of just class_weight="balanced"?
Both address imbalance, but differently. Class weights penalise the model more for getting fraud wrong during training — it's cheap and often good enough. SMOTE synthetically generates new fraud examples so the model sees more diverse fraud patterns to learn from. We used SMOTE because it tends to produce better decision boundaries for tree models; with Logistic Regression, class weights often suffice. The key point: whichever you choose, apply it after splitting, on the training set only.
Q: Why is PR-AUC your primary metric and not ROC-AUC?
ROC-AUC measures the tradeoff between true positive rate and false positive rate. With 99.83% legitimate transactions, even a weak model has a very low false positive rate — making ROC-AUC look great when it isn't. PR-AUC focuses entirely on the minority class (fraud), asking: across all thresholds, how well does the model balance catching real fraud vs. raising false alarms? In imbalanced classification, PR-AUC is the honest metric.
Q: What is data leakage and how did you prevent it?
Data leakage is when information from the test set influences model training, making evaluation unrealistically optimistic. I prevented it by: (1) splitting before scaling — the StandardScaler is fit only on training data; (2) applying SMOTE only to the training set — no synthetic examples in the test set; (3) never looking at the test set to make any modeling decisions. The test set is touched exactly once: final evaluation.
Q: XGBoost won on PR-AUC but Random Forest has a higher F1 — which would you deploy?
It depends on the operational cost of false positives vs. false negatives. Random Forest has higher F1 at the 0.5 threshold (0.754 vs. 0.687) — meaning fewer false alarms per caught fraud case at that specific cutoff. XGBoost has better PR-AUC (0.812 vs. 0.786) — meaning it has more flexibility across all thresholds. If a fraud analyst reviews every flag, I'd tune XGBoost's threshold to match the analyst's review capacity rather than use the default 0.5. PR-AUC is a better guide for threshold-tunable deployments.
Q: What would you do to improve this model further?
Several directions: (1) Feature engineering on the PCA components — while we can't interpret V1–V28 directly, we could create interaction terms or polynomial features. (2) Threshold optimisation — choose the operating point on the PR curve that matches the actual cost ratio of false positives to false negatives in the business. (3) Ensemble stacking — combine XGBoost and Random Forest predictions. (4) Temporal validation — since this is transaction data, a time-based split (train on earlier months, test on later) is more realistic than a random split. (5) Anomaly detection as a second layer — flagging statistical outliers alongside the classifier.
Q: What do the SHAP values tell you about what the model learned?
The SHAP summary shows V14, V4, V12, and V17 as the most influential features — these PCA components likely encode patterns the original Visa feature team identified as fraud-relevant when constructing the PCA space. That's reassuring: the model isn't latching onto noise or Amount alone. The waterfall plot for individual transactions shows whether a specific transaction was flagged because of unusual V14 values, unusually high amount, or a combination — giving an auditable reason for each decision rather than a black-box score.
